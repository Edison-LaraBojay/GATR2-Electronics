--- [critical] Bus timing / reply deadline (spec section 3): The reply deadline is measured from the host time the Pi read the request, not from when the request arrived. The claim that a Pi reply always starts before the Brain gives up only holds if the Pi reads within one 10 ms loop period of arrival, and nothing guarantees that. It fails when (1) the estimation worker overruns (the worker resyncs instead of bursting); (2) bytes pile up between SerialPort::open and the start of the workers, or while System::reset has the workers joined; (3) Loop rate_hz is set lower (a checked-in profile uses 30 Hz: 3+33+15+5.1 = 56 ms, more than the 50 ms Brain timeout). In each case the Pi can start transmitting after the Brain timed out and began its retry or next request, so both sides drive the bus. The same applies to session-A requests sitting in a backlog: the Pi transmits kResultUnknownSession while session B owns the bus. Newest-request-wins only considers COMPLETE frames. If one drain returns an abandoned complete request followed by a partial newer one, the Pi replies to the old request while the Brain is still mid-transmission.
  FIX: Anchor the deadline to the earliest possible completion time: the host time of the previous drain that did NOT complete this frame. Reply only if now <= prev_drain_time + reply_deadline. Frames completed in the first drain after open, startup or reset get no reply (or tcflush RX in reset). Suppress the reply if any byte followed the processed request in the same drain, or if a non-consuming check (ioctl FIONREAD on the link) just before asserting DE shows pending input. At build time, reject a brain_link profile where 1000/loop_rate_hz plus a processing margin >= deadline_ms. Replace the fixed 50 ms with a documented formula: Brain timeout > request airtime + V5 TX latency + reply_deadline + max reply airtime + tty RX latency + margin (e.g. deadline 20 ms, timeout 50 ms). Test backlog-after-stall, trailing-partial-frame and startup-backlog cases.
--- [major] Pi dedupe / SET_POSE retries (spec section 4): Duplicate detection only compares against the single last processed request_id, and any other id counts as new. The spec does not forbid the client from sending GET_STATE between SET_POSE attempts, and the control loop needs fresh state, so an implementer will naturally interleave polls. Trace: SET_POSE rid=10 is applied (init_sequence 4) but its Ok reply is corrupted. GET_STATE rid=11 is sent, so last processed = 11. The SET_POSE retry with rid=10 is then treated as new, init_sequence becomes 5, and localization re-anchors to the old pose, teleporting the robot if it has moved. The same happens on a Pending retry. request_id wrap (65535 -> ?) is also undefined, and an older id is never rejected.
  FIX: For each session, record the newest processed rid (compared with 16-bit serial arithmetic; wrap 65535 -> 1, skipping 0), plus the last SET_POSE (rid, placement sequence) and the last SELECT (rid, result). For a rid that is not newer: if it matches one of those records, give the duplicate answer; otherwise reply with a new kResultStale (or InvalidArgument) and apply nothing. State explicitly that GET_STATE may interleave while a SET_POSE is unresolved. Define kTimedOut as 'outcome unknown' so the app never assumes 'not applied'. Add a test: SET_POSE, GET_STATE, then a SET_POSE retry applies once.
--- [major] Brain client: in-flight state-changing requests across session change (spec section 4, Brain side): Only the kResultUnknownSession branch fails the in-flight placement with kSessionLost. The pi_instance-change branch just drops the session and re-HELLOs, and nothing says a retry must carry the session it was first sent in. If the client checks pi_instance first, or stamps outgoing requests with the current session, a still-pending placement ticket goes out again after re-HELLO as a NEW SET_POSE in the new session. The Pi applies it, so a placement from before the Pi restart relocates the restarted Pi. The same hazard applies to a SELECT retry. It is also unspecified whether the pi_instance check runs before or after correlation. A stale reply from the old instance, checked before correlation, would tear down a fresh session.
  FIX: Bind every request to the session it was first sent in; a retry is byte-identical to the original (same session, rid, op and body). ANY session change (UnknownSession, pi_instance change, local re-HELLO, a HELLO reply with a new session) terminates all in-flight state-changing tickets with kSessionLost before the next transmission. Apply the pi_instance rule only to replies that already passed correlation (op + rid + session/nonce).
--- [major] Pi restart / System::reset: configured anchor reported as localized: After a Pi process restart or System::reset, LocalizationExecutor re-applies <InitialPlacement> (origin 'configuration') in the first cycle, which sets initialized=true. The spec maps that to kRobotLocalized. The Brain then gets a 'field' pose at the configured start position while the robot may be mid-field. The driver treats PoseValid && Localized && AgeKnown as valid, so a new command drives on an invented pose, which violates 'never substitute invented poses'. The Brain cannot tell a configuration anchor from a command anchor. --- [major] Half-duplex DE release and loop budget (spec sections 3 and 5.1): The spec bounds only the DE-assert side. On the release side, the proposed transmit_timeout_ms=50 lets a transmitter that never reports empty hold DE high for up to 50 ms. Preemption between TX completion and the sysfs DE write is also unbounded on a non-RT kernel. Either delay exceeds the Brain's 3 ms request_gap, so the Brain's next request collides with the Pi's still-enabled driver. Separately, the reply is written synchronously in the estimation worker: 59 B at 115200 is about 5.1 ms plus TEMT polling, which is half of a 10 ms cycle whenever the Brain polls back-to-back. That makes the loop overruns in the critical issue more likely. The Brain poll period is not specified.
  FIX: Derive the TX timeout from the frame: bytes*10/baud + about 1 ms, never a fixed 50 ms. Make request_gap at least about 5 ms and larger than post-guard plus expected release latency. Count DE hold time beyond the TX end (a 'late_release' LinkStats counter) and document it as a residual risk alongside the assert side. Specify a Brain GET_STATE poll period (e.g. 20 ms) and state that TX time counts against the estimation loop budget.
--- [major] Byte-stream hygiene / stale bytes (spec section 2.1 FrameReader): 'Rejects and rescans exactly like today' means: on a CRC failure, drop the whole buffer (len_=0) without rescanning the buffered bytes for a later sync. With a length byte, a corrupted len of 122 or less makes the reader swallow up to 128 following bytes. On the Brain, a truncated reply (collision, or a Pi killed mid-TX) therefore also destroys the next reply. On the Pi, one corrupted request length can swallow several ~14-26 B retries (about 0.5 s of lost polls). Stale bytes left in the Brain RX buffer before a request can also be parsed as a reply to that request.
  FIX: Brain client: before sending each request, drain RX and reset the FrameReader. With one outstanding request, anything received before the send is stale by definition. Pi collection: discard a buffered partial frame when a drain returns no new bytes, since requests are sent in one burst. Per direction, bound v3 len (e.g. request payload <= 32, reply payload <= 64) so implausible lengths reject immediately. Test truncated-then-valid reply and corrupted-length-then-retry.

Worse, require_observed_landmark defaults to false, so a relative command often first resolves on the nominal map pose. The checked-in camera pipelines use LandmarkEstimation blend="1.0", so the first observation replaces nominal in one step. That step equals the full physical displacement of the landmark plus localization error. The command then fails with kLandmarkJump at the exact moment vision starts helping, or max_landmark_jump has to be set so large that it bounds nothing. The nominal->observed transition is not defined at all.
  FIX: Define the jump as the change between consecutive accepted candidates of the same source (per new estimate), not candidate vs destination. The destination separately follows the latest accepted candidate at landmark_follow_speed / landmark_follow_turn_rate, with shortest-angle heading. Define the source upgrade explicitly: the first kObserved candidate after nominal resolution is accepted if within max_nominal_correction (its own default, larger than max_landmark_jump). It becomes the new reference, and phase selection reruns if the robot is outside position_tolerance. Alternative: make require_observed_landmark default true and nominal opt-in. Add tests: a 10 cm nominal->observed step completes; a 50 cm step fails with kLandmarkJump; slow drift above follow speed does not spuriously fail.
--- [major] Frame capture race after placement (4, 6.2, 7): After a Brain reboot the Pi is still localized (by design), and profiles with InitialPlacement are localized from boot. Ready requires a GET_STATE Ok, so the driver's cache holds a Localized pose under the OLD anchor_revision. initialize() then submits SET_POSE and waits for Applied. If a command starts before the next GET_STATE refreshes the cache, the Navigator captures the old frame and drives on the old-anchor pose. The next reply bumps generation and the command fails with kFrameChanged. This hits the essential reboot scenario, and simulated tests will be flaky. The SET_POSE Ok body already carries the new odometry_epoch/anchor_revision, but the spec never uses it.
  FIX: In NavigatrDriver: when a placement result becomes Ok, record its (odometry_epoch, anchor_revision) and mark cached robot and landmark input unusable until a GET_STATE reply reports that anchor or a newer one. Report the ticket as kApplied only after that state has been received, or expose 'applied and frame current'. Then investiGATR never sees a pre-placement pose after Applied. Add this to the reboot test: session B, Pi already localized, SET_POSE applied, then an immediate goTo completes without kFrameChanged.
--- [major] Connection loss vs input loss semantics (6.2, 7; requirement 'Loss of the connection ... must not silently continue an old movement'): The Navigator treats every unusable snapshot the same way: kWaiting, then resume if input returns within input_loss_timeout. For NavigatrDriver the spec never defines when 'connected' becomes false or what link_age is measured from. A cable glitch or several dropped transactions that keep the same Pi session and frame will therefore resume the old movement after reconnection, with the value of input_loss_timeout unstated. Whether that counts as 'silently continuing' depends entirely on unspecified numbers, and two implementers will define 'connected' differently.
  FIX: Define for NavigatrDriver: connected = session ready AND the last correlated reply was received within link_timeout (default e.g. 0.25 s); link_age = now - that receive time. In the Navigator: connected == false during an active command -> kFailed/kInputLost immediately, no resume. Connected but pose stale or invalid -> kWaiting with zero output, resume allowed only within a short input_loss_timeout (default e.g. 0.3 s) and the same frame. State that a session change during a command fails it (kFrameChanged or kInputLost; pick one and test it).
--- [major] Slew vs zero-output rules (6.2): 'Outputs clamped then slew limited' does not say whether decreases are slewed. Only the unusable-input case says zero bypasses slew. Cancel, completion, timeout, failure and idle say 'zero output' without saying whether it is immediate. With symmetric slew, cancel and disable do not stop the motors right away, which contradicts 'disable/cancel stops outputs'. Driving->Aligning also coasts on a slewed forward ramp-down, which feeds the Aligning dead band above.
  FIX: Use one rule: the slew limit applies only to increases in |output| (a sign reversal first drops to 0 immediately). Decreases toward zero are immediate. Every terminal state, kIdle, kWaiting (input or landmark) and unusable input return exactly {0,0} and reset slew memory to zero. Replacement keeps slew memory. Test: cancel mid-drive gives exactly zero on the next update(); arrival does not ramp down.
--- [major] Unspecified numbers, scopes and constraints (6.2, 7): The spec names about 20 parameters without defaults, units or ordering constraints: max_pose_age, max_link_age, input_wait_timeout, input_loss_timeout, default motion timeout, max_landmark_age, max_landmark_jump, landmark_follow_speed/turn_rate, turn_exit, turn_in_place_threshold, heading_correction_min_distance, position_tolerance, reenter_distance, heading_tolerance, waypoint_pass_radius, settle_time, max_dt, integral_limit, max_forward/max_turn, slew rates, and the PID gains (units 1/m and 1/rad on normalized demand). Scopes are also missing: is the timeout per path or per waypoint, and does it include kWaiting? For a relative waypoint later in a path, is the landmark wait measured from command start (which would fail immediately) or from waypoint activation? The Brain GET_STATE poll interval is unspecified ('polling the driver every few ms'). Yet driver age = reported age + RTT + (now - receive time) must stay under max_pose_age. A tight max_pose_age will flicker between Waiting and moving. The sim tests' pass criteria depend on all of this. Invalid config behavior is not defined.
  FIX: Add a NavigatorConfig table: name, unit, example default marked as a tuning starting point, and validated constraints (arrive_distance < position_tolerance; turn_exit < turn_in_place_threshold; waypoint_pass_radius >= near_distance; max_dt > 0; gains >= 0; kI = 0 in examples). Define an invalid config as failing every command with kInvalidCommand. State: the motion timeout covers the whole command including waiting, counted from the first update(); the landmark wait is measured from that waypoint's activation. Specify the driver's GET_STATE poll interval (e.g. 20 ms) and how GET_STATE interleaves with SELECT/SET_POSE so state cannot starve, plus the rule max_pose_age >= poll interval + response timeout + typical Pi pose age. Document that the controller does not compensate for latency.
--- [minor] Per-update ordering and status details (6.2): The spec does not give the order of checks within one update, so two implementers will give different results when events coincide (timeout vs completion, frame change vs unusable input). Other gaps: the state and output while the robot pose is fine but a relative waypoint is unresolved; settle-timer reset triggers; the fact that request() fires only on edges, so after setSource the new source never receives the current need and the old source keeps its landmark selected; how a caller detects that its command was replaced.
  FIX: Specify the order: terminal -> zero; timeout; frame check; input usability; landmark resolution; phase/control; completion. An unresolved relative waypoint means kWaiting with zero output. The settle timer resets on leaving the condition, on any unusable cycle, on a phase change, and on a gap between updates > max_dt. Call source.request(current_need) on every update(); it is already idempotent. On setSource, send request({}) to the old source. Implement goTo/goToRelative as one-stop-waypoint follow(). Document that waiters compare status().command_id to their own id (a mismatch means replaced).
--- [minor] Angular PID wrap and forward-only (6.2): Errors are wrapped, but the derivative of an angular error must also use the wrapped difference. When the destination is roughly behind the robot, eb can flip between +pi and -pi, producing a derivative spike and turn-direction chatter. 'Forward only, no reverse driving' is not guaranteed either: the drive PID's D term can go negative, and max(0, cos eb) does not remove that sign.
  FIX: For angular PIDs, compute the derivative as wrap(e - e_prev)/dt. When |eb| > pi - small_band (e.g. 5 deg) in Turning, keep the previous turn sign. Either clamp forward to [0, max_forward] or explicitly allow negative forward as braking and drop the 'no reverse' wording.
--- [minor] Fallback procedure (6.3; requirement 'a fallback must supply a real valid pose in a known frame'): align() requires a valid, fresh Navigatr snapshot. The scenario that needs a fallback is Navigatr disappearing, and at that point no fresh snapshot exists. Under the spec's own rules, switching on loss is impossible unless the odometry source was already aligned while Navigatr was healthy, and the spec never says so. Aligning a moving robot with a pose that is age seconds old also bakes in error of speed x age.
  FIX: Document the procedure. While Navigatr is usable and the odometry source is not active, re-align odometry from fresh snapshots (each align creates a new generation, which is harmless while that source is inactive). On Navigatr loss the app explicitly calls setSource(odometry); the active command is cancelled and the app issues new commands. Align only from a snapshot with age <= max_pose_age, preferably while stationary, and document the speed x age error. Test: aligned odometry takes over after loss; odometry that was never aligned reports invalid.
--- [minor] Type simplifications (6.1): FrameRef.session is redundant for NavigatrDriver, because generation already increments on any (pi_instance, session, epoch, anchor) change, and it is undefined for OdometrySource and SimulatedSource. The spec also does not say that a valid robot must never come with generation 0. LandmarkId is uint16 while the wire landmark_id is u8 with 0 meaning none, so ids 0 and >255 behave unspecified. The clause 'Also when a waypoint's destination was resolved under an earlier frame' can never fire separately, because any frame change already fails the command.
  FIX: Replace FrameRef with a single uint32_t frame_generation, unique per source instance, 0 = none. A snapshot with robot.valid and generation 0 is unusable. Keep the Pi session only as NavigatrDriver diagnostics. Reject goToRelative with id 0 as kInvalidCommand, and document that NavigatrDriver reports ids outside 1..255 as unavailable.
