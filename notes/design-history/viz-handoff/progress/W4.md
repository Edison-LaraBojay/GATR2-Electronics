## Codec API summary (for W3, W5, W1)
- `encodeBrainRequest`/`decodeBrainRequest` handle `kOpTelemetry` (12): request payload is exactly 8 + 54 = 62 bytes (68-byte frame). The body is `BrainRequest::telemetry`.
  - Encoder writes zeros for every group whose flag bit is clear; refuses (returns 0) a wheels group with `wheel_count > kTelemetryWheelsMax` (6).
  - Decoder zeroes every group whose flag bit is clear, whatever the wire holds; keeps unknown flag bits in `flags`; a wheels group with `wheel_count > 6` is a decode failure (false).
  - Replies to TELEMETRY are header only for every known result (`brainReplyMinLen(12, r) == 13`).
- `picoCommandLen(kPicoOpDiagnostics) == 7`; the body byte is `PicoCommand::diag_hz`. The codec carries any byte; the Pico refuses 6..255 with BadBody.
- `encodePicoDiag(const PicoDiag&, buf, cap)` / `decodePicoDiag(buf, len, PicoDiag&)`: frame 0x14, payload 26, frame 32 bytes. Decode needs version == kPicoLinkVersion and the exact length.
- For records that keep raw bytes (hub `DiagBrainTelemetry::body`, `DiagPicoDiag::payload`): `decodeTelemetryBody(body, 54, BrainTelemetry&)` and `decodePicoDiagPayload(payload, 26, PicoDiag&)` (same rules). W1 and W3 should use these instead of rebuilding frames.
- `FrameReader` accepts 0x14 (len must be 26) and fills `FrameReaderStats` (`stats()`):
  - `bytes`: every pushed byte; `frames`: every reported frame (push or next);
  - `sync_dropped`: every discarded byte, including the sync byte of a rejected candidate (the rest of a rejected candidate is rescanned). Without reset(): bytes = reported frame bytes + sync_dropped + buffered;
  - `length_errors`: rejected candidates with impossible length, type or sensor mask; `check_errors`: rejected candidates failing CRC/checksum. These count candidates, not bytes.
  - `reset()` clears the buffer, never the stats.
- Known-byte vectors come from an independent Python packer: `$S/w4-vectors/pack.py` (output in `$S/w4-vectors/vectors.txt`).

## Risks
- Nothing is validated on hardware: DIAGNOSTICS and 0x14 on the real UART, `gpio_get` read-back of pins in UART/SPI function (relies on the RP2040 pad input being readable in any function), the 32-byte frame filling the TX FIFO without blocking (arduino-pico `write` waits only when the FIFO is full; checked in its source), TELEMETRY over USB NG1 and RS-485, the camera.
- The Brain attitude is stamped with the Pi arrival time, so it lags the Brain sample by up to one telemetry period plus link latency (about 100 ms at the planned rate, latency unmeasured). The 250 ms freshness leaves about two missed reports of margin.
- VEX roll/pitch sign conventions and the mounting yaw are the Brain's (W5), documented UNVERIFIED.
- DIAGNOSTICS shares the Pico command queue and 100 ms command gap with CONTROL 3/4: right after a Pico boot a CONTROL can go out up to 100 ms later.
- A deaf Pico (Pi TX wire open) gets a DIAGNOSTICS attempt every ~7 s forever (10 small frames per attempt); harmless but visible in raw bytes.
- The camera preview config refuses to start on a binary built without libcamera (existing libcamera_camera behavior, documented); a missing or failing camera at runtime is only a warning.
- `last_frame_ms_ago` style ages are computed against the process HostClock; under inline test clocks they can be meaningless (written as null when negative).
