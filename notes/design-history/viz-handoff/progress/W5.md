## CONTRACT ISSUES
1. "must not delay state polls" (spec 8) is not achievable literally at the defaults. TELEMETRY never takes the turn of a due poll and goes only in the first slot right after a state reply, but with one request outstanding its exchange (RS-485 68+19 bytes, ~9.8 ms, plus the 5 ms gap) is longer than the ~5 ms idle window after a state exchange, so the next poll is pushed back. Final code, host fakes, 3 s, telemetry at 10 Hz: RS-485 bus polls 145 -> 130..133 (-8 to -10%), longest poll gap 21 -> 32 ms; fake USB 145 -> 133..137 (-6 to -8%), longest gap 21 -> 30 ms. A strict fit rule would never send at these timings. The VEX IMU samples ride on GET_STATE and slow by the same fraction (still far inside the Pi's 250 ms staleness limit). Mitigations available: gatr2_robot::kSendTelemetry = false, or kTelemetryPeriodMs 200. Lead decision wanted if 10 Hz is not acceptable.
2. RESOLVED at integration (kTelemetryTarget, see INTEGRATION). No validity bit for the motion group's target. With no resolved destination (idle, waiting for a reference) target_x_mm/target_y_mm/target_heading_cdeg are 0, indistinguishable from a real target at the field origin. Proposal (lead + W4 + W1/W2): TelemetryFlagBit kTelemetryTarget = 1u << 3, "target_* valid (MotionStatus::has_destination)". W4's decoder keeps unknown flag bits, so an older Pi ignores it. Until decided, W1/W2 should treat target (0, 0, 0) as missing or draw it only while motion_state is 2 (running) or 3 (settling). Brain side is a 2-line change (actugatr/src/telemetry.cpp, and kTelemetryFlags in communigatr/src/client.cpp) plus a test.
3. (info for the lead) pi/naviGATR/tests brain_link_e2e compiles brain/communiGATR/src/client.cpp and brain/actuGATR/src/drive.cpp: both changed, no new source dependencies (client.cpp only uses the translaGATR codec). The new sources attitude.cpp / telemetry.cpp are not needed there. Not built by W5 (lead-owned Pi CMake, other workers mid-edit).
